Root Cause Summary
The conversion-workflow module's multiplication OpenAPI spec (multiplication.yaml:44-47) declares:


content:
  text/plain:
    schema:
      type: number
      format: float
This causes the OpenAPI code generator to produce a REST client interface that expects to deserialize a text/plain response body into java.lang.Float. In native image mode, RESTEasy doesn't have a MessageBodyReader registered for text/plain -> Float, so it fails with RESTEASY003145.

All three other variants (conversion-workflow-full, conversion-workflow-function, conversion-workflow-spec) already use application/json with a proper wrapper object — and they work fine.

The Fix
The simplest and most consistent fix is to align conversion-workflow's multiplication spec with the pattern used by the other variants — change the response content type from text/plain (raw float) to application/json (wrapped in an object). This also requires updating the mock service and the test assertion.

multiplication.yaml — change response from text/plain: float to application/json: {product: float}
OperationsMockService.java — change the multiplication mock to return JSON with {product: 37.808}
ConversationFlowIT.java — the test should still work since the workflow's actionDataFilter maps {product: .}, which would now receive the JSON object directly
fahrenheit-to-celsius.sw.json — update the actionDataFilter since the response is now an object with a product field instead of a raw value

It was likely never tested in native mode after the text/plain change
The key evidence:

Commit 0495d809 (Aug 2024) deliberately changed the multiplication spec from application/json to text/plain with Quarkus 3.8.4. The commit message says "This illustrate the usage of functions that returns not json objects".

The test class ConversationFlowIT uses @QuarkusIntegrationTest, which runs in both JVM and native mode — but native mode only activates when built with -Dnative. In JVM mode, reflection works unrestricted, so Float.valueOf(String) is always accessible and the test passes fine.

There's no evidence native tests were run for this specific example after that change. The subsequent commits are just Quarkus version bumps (3.8.6 → 3.15 → 3.20 → 3.27).

So this is a pre-existing bug, not an upgrade regression
The DefaultTextPlain.isReadable(Float.class) calls TypeConverter.isConvertable(Float.class), which tries Float.class.getDeclaredMethod("valueOf", String.class) via reflection. In any GraalVM native image without explicit reflection registration for Float, this would fail — regardless of Quarkus version. The issue was introduced in Aug 2024 but was masked because native mode was never exercised for this test.

That said, there's a secondary factor: Quarkus has been progressively tightening which built-in providers get included in native images to reduce binary size. It's possible that in older Quarkus versions, some broader reflection registration incidentally covered Float, but this would have been an accidental side-effect rather than deliberate support.

Bottom line: The fix in ServerlessWorkflowAssetsProcessor.java is the right approach — it explicitly registers primitive wrapper types for reflection so that text/plain responses can be properly deserialized in native mode, regardless of Quarkus version.
